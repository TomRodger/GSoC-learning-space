## Why Mesa
<!-- What drew you to Mesa specifically? Have you used it before? How did you find it? -->
Before taking on this project, I had never used Mesa before. But once I read up on it, I found myself completely invested. In this time I dedicated a large chunk of my days reading through the Git discussions, understanding the Mesa codebase, and then what I most enjoyed, creating the models. I built two models, ran hundreds of batch-comparisons, got stuck on things, figured them out, and wrote up what I found honestly; including the findings that didn’t show what I had hoped they would. That is how I approach problems: build first, understand through doing, and then document what true findings come from it. 

The Mesa API and codebase was fairly simple to pick up, and once I got on to working through advanced models, it made the Behavioural Framework problem clear, with the current structure fighting you when you try to implement drive-based agents or more. Building both the monolithic step() and refactored behavioural versions of Sugarscape made the current limitations clear. Comparative analysis of these versions felt natural using the integrated Python ecosystem (since I was already familiar with the tools), and being able to pipe DataCollector output straight into pandas and matplotlib for the 100-seed batch comparison made the analysis feel like an extension of work I was doing already in my data science coursework, rather than learning a whole new stack. Using Solara for visualisation and more plotting helped debug and adjust the code and will be a very useful development tool going forward.

## Where I want to go
<!-- What's your goal with contributing to Mesa? What kind of contributions do you see yourself making? -->

Long term, this project is my entry point into the space I want to work in. Working on the Behavioural Framework has made me realise that the Behaviour class pattern (score, choose_action, act) is not just a Mesa abstraction. It is a general architecture for any decentralised system where individual agents need to weigh competing drives and act without central coordination. 

Watching emergent collective behaivour appear bottom-up in Mesa models got me thinking about what this looks like on physical hardware. That thought pulled me in to researching swarm robotics, and it has been at the front of my mind since. The core idea that draws me in is simple: small robots running identical behavioural firmware, communicating only locally, producing emergent collective behaviour without any central coordinator. A framework that runs the same agent architecture in Mesa simulation and on physical hardware simultaneously, so simulated and real emergent behaviour can be formally compared and the gap between them understood.

This is something I want to build seriously over time, starting independently and later bringing in collaborators and resources as the project develops. Mesa this summer is where the foundation gets built. To build a system where the same behavioural architecture runs identically in simulation and on physical hardware, you first need to deeply understand how agent-level decision structures produce emergent collective behaviour, and where and why simulation diverges from reality. That undestanding does not come from just reading about it. It comes from building models, measuring what actually emerges, and being wrong about what you expected. That is what this summer gives me. 

Past this Summer, I would also like to stay involved with the Mesa community and problem space, as I have really enjoyed my engagement with Mesa in my time spent doing pre-work for this project. I could look to maintain the work I build in Summer, contribute to related discussions, or come back to Mesa with new skills as my degree progresses. If I take Machine Learning, that opens reinforcement learning-based agent behaviour as a direction; something the framework would need to support. If I take NLP, that connects directly to Mesa-LLM and the question of how language-driven agents fit into a behavioural architecture. The framework I build this Summer is a foundation I will want to extend, not a project I will just close and forget.
